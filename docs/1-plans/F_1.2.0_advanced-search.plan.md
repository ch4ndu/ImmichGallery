# Advanced Search Implementation Plan

## Overview

Version 1.2.0 expands the existing Explore/Search surface into a read-only,
composable Advanced Search experience across Android, iOS, and JVM Desktop. It
adds Context, Filename, Description, and OCR text modes plus People, Albums,
Tags, Camera, Location, taken-date, media, Motion Photo, Favorites,
Not-in-album, visibility, and rating filters while preserving the existing
live-only justified result grid, server pagination, viewer, stack browsing, and
return targeting.

The feature follows Immich's current user-facing search concepts but does not
expose raw server filesystem paths or internal `MetadataSearchDto` fields.
Person selection is a core requirement: a compact searchable picker reuses the
existing Room-backed People list, authenticated thumbnails, and exact
`personIds` filtering. Find Similar remains a separate future viewer action.

## Problem Statement

Explore currently supports only a nonblank text query and two modes: Smart and
Filename. It cannot compose text with metadata constraints, perform filter-only
searches, gate Context/OCR against server capabilities, or select exact People,
Albums, Tags, dates, media properties, cameras, locations, visibility, or
ratings. The current request identity is only `(query, type, generation)`, so it
cannot safely bind pagination and stale-response rejection to an applied filter
snapshot.

Most user photos do not have GPS data, making a Places-first feature a poor
discovery investment. Advanced Search instead improves discovery across the
whole accessible library, including non-geotagged assets, without adding a new
top-level destination, Room result cache, or server mutation capability.

## Solution Architecture

Introduce one immutable domain `SearchCriteria` and one submitted
`SearchSession`. Editing controls and an open filter editor remain drafts;
applying or removing a filter creates a new normalized criteria snapshot,
selects the Smart or Metadata endpoint once, cancels the preceding session, and
starts page one. Every response, retry, load-more request, and row-packing
publication must match the submitted criteria, endpoint, generation, and page
token rather than rereading mutable UI state.

Text dispatch is endpoint-specific:

- Nonblank Context text uses `POST /api/search/smart`.
- Filename, Description, and OCR text use `POST /api/search/metadata`.
- Any filter-only search uses Metadata regardless of the currently selected
  text mode.
- Context is never silently rerouted to Metadata when unavailable or rejected.

The Search repository owns exact endpoint-specific JSON construction, including
the distinction between an omitted field and explicit JSON `null`. Endpoint
selection is a pure, pre-I/O domain operation: `SearchViewModel` normalizes the
current visible criteria, chooses the endpoint, and freezes both into
`SearchSession` before launching page one. A single `SearchAssetsUseCase`
accepts that frozen endpoint/criteria pair, validates that they agree, performs
the call, preserves cancellation, and maps supported IMAGE/VIDEO results.
`SearchViewModel` continues to own result state, paging, row projection, viewer
callbacks, and layout density; it additionally observes existing Album and
People UseCases and exposes lazy live option data through focused search
UseCases.

Search results, server features, preferences, tags, and camera/location
suggestions remain memory-only for the Explore destination lifetime. Existing
People and Album lists remain Room-backed re-fetchable caches. No database
entity, DAO, migration, persistent saved-search setting, route, or platform
`expect`/`actual` is added.

**Current state**:

`SearchType` is a UI enum with only `SMART` and `METADATA`. The query and type
are stored directly in `SearchState`, and `SearchResult` contains supported
assets plus a parsed numeric next page. There is no domain representation for
advanced criteria, explicit Unknown/Untagged/Unrated values, endpoint choice,
or applied request identity.

**Modifications**:

- Add immutable `SearchCriteria` with the editable query, text mode, stable
  ordered Person/Album id lists, tag constraint, camera and location
  constraints, inclusive taken-date range, media type, Motion-only flag,
  Favorite flag, Not-in-album flag, visibility, and rating constraint.
- Add `SearchTextMode` values for Context, Filename, Description, and OCR.
  Full/server-path mode is deliberately excluded.
- Model fields that distinguish no filter from an explicit missing value with
  narrow semantic types: location/camera values support Any, Unknown, and an
  exact string; tags support Any, Untagged, and selected ids; rating supports
  Any, Unrated, and one through five stars.
- Use stable ordered id lists with deterministic de-duplication instead of
  unordered sets in the submitted contract. Display labels and thumbnails are
  resolved from current option data and are not authoritative request values.
- Add media values All, Image, and Video plus a separate Motion-only boolean.
  Normalization makes Motion-only imply Image and prevents a contradictory
  Video-plus-Motion request.
- Add visibility values All Accessible, Timeline, and Archive. All Accessible
  omits `visibility`, preserving current Search inclusion of appropriate
  timeline-enabled partner content; Hidden and Locked are not exposed.
- Normalize Albums and Not-in-album as mutually exclusive. Applying Albums
  clears Not-in-album; applying Not-in-album clears selected Albums.
- Define an explicit empty-criteria predicate. Blank text with no filters
  returns to Explore and never performs an unbounded search; blank text with at
  least one filter is a valid Metadata search.
- Define `SearchEndpoint`, a pure `selectSearchEndpoint(normalizedCriteria)`
  operation, and an immutable submitted `SearchSession` carrying normalized
  criteria, the chosen endpoint, generation, current/next page, and consumed
  pages. `SearchViewModel` invokes the pure selector before any I/O, freezes the
  result for pagination/publication identity, and passes it into the UseCase.
- Preserve `SearchResult` as the live supported-asset result and numeric server
  page boundary unless implementation evidence requires a compatible typed
  error wrapper; do not introduce a generic pagination framework.
- Add focused pure tests for empty detection, stable de-duplication, whitespace
  normalization, Motion/Video normalization, Album/Not-in-album exclusivity,
  date ordering, and every tri-state constraint.

- `composeApp/src/commonTest/kotlin/com/udnahc/immichgallery/data/remote/AdvancedSearchRequestBuilderTest.kt` (new)

**Current state**:

`ImmichApiService.searchSmart` serializes only `query`, page, and size, while
`searchMetadata` serializes only `originalFileName`, page, and size. Private
serializable DTOs rely on a shared JSON configuration with
`encodeDefaults = true`. The service has no reads for server Search features,
user Search preferences, tags, or Search suggestions.

**Modifications**:

- Replace the two narrow Search request DTOs with internal endpoint-specific
  request builders that deliberately add JSON keys. Do not create a nullable
  superset serializable DTO: default nullable fields would serialize as `null`
  and incorrectly mean Unknown, Untagged, or Unrated.
- Map Context text only to Smart `query`; map Filename to
  `originalFileName`, Description to `description`, and OCR to `ocr` in a
  Metadata body. Never place both Smart `query` and a future `queryAssetId` in
  one request.
- Add common filters to both endpoint bodies where the current Immich contract
  supports them: `personIds`, `albumIds`, `tagIds`, country/state/city,
  make/model/lensModel, `takenAfter`, `takenBefore`, asset `type`, `isMotion`,
  `isFavorite`, `isNotInAlbum`, `visibility`, and `rating`.
- Omit empty id arrays and all Any/no-filter values. Encode Unknown camera or
  location, Untagged, and Unrated as explicit JSON `null` only when the user
  chose those values.
- Encode multiple People, Albums, and Tags exactly as stable id arrays. Document
  and test Immich's intersection semantics: results contain all selected ids;
  selected parent Tags include descendant-tag matches according to the server.
- Use page size 50 and the requested numeric page. Continue accepting only the
  server-returned `nextPage`, validating malformed, repeated, backward, and
  already-consumed values without synthesizing a page.
- Match accepted Immich Web date semantics: resolve the selected start date to
  00:00:00 and end date to 23:59:59.999... using UTC labels while preserving
  the selected calendar wall-clock boundaries. `takenAfter` and `takenBefore`
  are inclusive. The immutable submitted request must not change after a
  device time-zone transition.
- Keep `withDeleted`, Locked/Hidden visibility, EXIF/People response expansion,
  internal paths, checksums, library id, encoded/offline state, and other raw
  DTO controls omitted. Preserve current server-default stack-primary behavior
  rather than guessing a new `withStacked` value.
- Add response models containing only consumed fields from
  `GET /api/server/features` (`search`, `smartSearch`, and `ocr`),
  `GET /api/users/me/preferences` (Tags and Ratings enabled values), and
  `GET /api/tags` (id, parent id, name, full value, and optional color).
- Add `ImmichApiService` reads for the public stable server-features endpoint,
  authenticated preference endpoint (`userPreference.read`), authenticated
  Tags endpoint (`tag.read`), and stable
  `GET /api/search/suggestions` endpoint (`asset.read`). Suggestions support
  Country, State, City, Camera Make, Camera Model, and Lens Model; decode the
  server's documented `string[]` plus its current possible `null` result when
  `includeNull=true`.
- Pass parent values for dependent suggestions: Country constrains State and
  City; State further constrains City; Make constrains Model and Lens; Model
  further constrains Lens. Do not treat suggestions as a provider for People,
  Albums, or Tags.
- Keep endpoint logging free of raw query text, selected names/ids, API keys,
  and credential-bearing URLs. Log only mode, endpoint, page, filter-category
  count, and response counts.
- Add exact JSON tests proving every field, endpoint-specific text mapping,
  filter-only mapping, omitted-versus-null behavior, stable id-array order,
  date boundaries including DST calendar dates, and rejected incompatible
  combinations.
- Extend decode contract tests for missing optional feature/preference fields,
  Tags, nullable suggestions, unknown future fields, and malformed page tokens.

**Modifications**:

- Replace String-based Smart/Filename methods with endpoint-specific advanced
  methods accepting normalized `SearchCriteria`, page, and size. The repository
  delegates exact body construction to `AdvancedSearchRequestBuilder` and does
  not expose JSON types above the data layer.
- Add repository reads for server features, user preferences, Tags, and typed
  suggestions. Preserve cancellation through `runSuspendCatching` boundaries.
- Add one `SearchAssetsUseCase` that accepts the endpoint already selected by
  the pure domain operation, validates it against the normalized criteria,

  claiming a server snapshot.

  feature results or disable baseline Metadata search.
- Add focused Tags and suggestion UseCases. Tags retain full hierarchy values

  server order and map `null` to explicit Unknown.

- Add tests for endpoint dispatch, blank-text filter dispatch, supported-type
  mapping, URL construction, cancellation propagation, partial capability
  failure, preference permission failure, suggestion normalization, Tags, and
  no Smart-to-Metadata fallback.

edits immediately invalidate requests and clear results. Search refuses blank
queries. Search and load-more redispatch from mutable query/type state, and row
publication matches only query/type/generation.

**Modifications**:

- Replace `SearchType` with domain `SearchTextMode`; retain the editable query
  and selected text mode separately from the last submitted `SearchSession`.
- Add applied metadata criteria, active filter summaries, capability/preference
  availability, Room-observed People and Albums, lazy Tags and suggestion
  states, and picker-local loading/error/retry indicators to `SearchState` or
  focused immutable nested state types.
- Keep open-editor draft values local to the filter host. Opening copies the
  currently applied criteria; Cancel, system Back, Escape, and sheet/dialog
  dismissal discard the draft; Apply normalizes and submits the whole draft
  atomically.
- Preserve current behavior in which editing the main query or text mode
  invalidates old search/page/layout work and clears executed results while
  retaining applied metadata filters. The next explicit IME/Search action
  combines the edited text/mode with those filters.
- Permit explicit Search when the text is blank but an applied filter exists.
  If both are empty, cancel the active session and return to Explore without a
  request.
- Applying a focused/consolidated filter draft or removing an applied value
  chip always submits the **currently visible** query and text mode together
  with the updated metadata filters. If the user edited text/mode after the
  preceding search, Apply/removal intentionally submits that edit rather than
  replaying the previous session's text. The same capability checks used by
  IME/Search run before this implicit submission.
- Removing an applied value chip immediately starts page one when the resulting
  visible text plus criteria remain nonempty. Removing the last criterion with
  blank visible text returns to Explore. `Clear filters` removes metadata
  filters but leaves the visible main query and submits that query when it is
  nonblank; clearing the query remains the text field action.
- For IME/Search, filter Apply, chip removal, and Clear filters, first snapshot
  the current visible text/mode plus resulting applied metadata criteria, then
  normalize it, select its endpoint with the pure selector, and freeze both in
  `SearchSession`. Search, retry, load more, result publication, and row packing
  must all match that session generation and must never read later visible
  edits or an open editor draft.
- Cancel search, load-more, row layout, option filtering, and dependent
  suggestion jobs when their owning generation/input changes. Keep the current
  atomic load-more claim and explicit retry behavior.
- Retain successfully consumed numeric pages even when a response maps to no
  supported assets. Terminate on repeated/backward/malformed pages, retain
  existing rows on later-page failure, and keep the exact retry page.
- Deduplicate appended assets by id while preserving first-seen order. A stale
  response, stale picker refresh, or completed old row-packing job must not
  publish into a newer criteria generation.
- Load server features and preferences only for the Explore/Search ViewModel
  lifetime, independently and retryably. Confirmed `search=false` disables
  execution without removing Explore cards; Context and OCR require positive
  capability knowledge. If Context is unavailable, preserve its draft text and
  ask the user to choose another mode rather than changing meaning silently.
- Observe People and Albums from Room immediately. On the first opening of each
  picker during the Search ViewModel lifetime, invoke its existing sync once;
  show cached options during that refresh and use the blocking picker-local
  loading/error path only when no cache exists. Do not invent a new staleness
  threshold.
- Load Tags only when its enabled editor opens. Load camera/location
  suggestions only when their focused editor opens; cache successful results
  by dependency tuple for the ViewModel lifetime. Changing Country/State or
  Make/Model clears invalid descendants and invalidates older suggestion jobs.
- Preserve applied ids when refreshed options no longer contain or cannot name
  them. Render an id-safe unavailable label and keep the chip removable rather
  than silently deleting a constraint.
- Add typed localized messages for unavailable Search capability, optional
  preference/filter data, People/Album/Tag picker failures, and suggestion
  failures without replacing the global Search failure state.
- Update Koin to replace the two old Search UseCases with the unified Search
  and option UseCases and inject existing People/Album UseCases into
  `SearchViewModel`.
- Expand ViewModel tests for filter-only search, immutable submitted sessions,
  Apply/Cancel boundaries, chip removal, final-filter Explore restoration,
  stale first/page/row responses, exact retry pages, duplicate ids, empty
  supported pages, capability gates, partial option failures, People/Album
  cached failure behavior, Tags, dependent suggestion races, and all existing
  density/viewer behavior.

## Technical Considerations

- **Layering**: Preserve API/Room -> repositories -> UseCases ->
  `SearchViewModel` -> Compose. JSON construction remains in the data layer;
  ViewModel injects unified Search/filter UseCases and existing People/Album
  UseCases, never repositories. Register every new UseCase in Koin and remove
  obsolete Smart/Filename registrations only after all call sites migrate.
- **Read-only scope**: Every endpoint is GET or read-only POST Search. No asset,
  Tag, rating, preference, Album, Person, or server mutation is authorized or
  introduced.
- **Cache ownership**: Search results and new optional filter data are
  destination-lifetime live state. People and Albums reuse existing Room-backed
  re-fetchable caches and logout cleanup. There is no Room schema/migration,
  saved-search persistence, or new setting.
- **Async correctness**: Criteria Apply, chip removal, query/mode edit, Clear,
  and return-to-Explore invalidate search/page/layout work. Dependent
  suggestion requests have their own input generation. Existing explicit
  page-retry and atomic near-end claim behavior remains. Partial option failure
  is localized and never disables unrelated metadata search.
- **UI and layout**: Reuse `ExploreRoute`, `SearchScreen`, justified rows,

## Edge Cases Considered

- Empty text plus no filters returns to Explore; it never enumerates the whole
  library. Empty text plus one or more filters is valid Metadata Search.
- Whitespace-only text is unset. Unknown is available only through an explicit
  Camera/Location picker choice.
- Context and OCR are unavailable until positively supported; loading or
  failure of those capabilities does not block Filename, Description, or
  filter-only Metadata search.
- A preference permission failure hides/disables Tags and Ratings editors while
  leaving all baseline filters operational. A Tag permission failure is local
  to the Tag picker.
- Empty People/Album caches trigger their established loading/sync path when
  opened. Cached selections stay usable during refresh failure.
- Unnamed People display as Unknown and remain selectable. Duplicate Person
  names remain distinct by id and thumbnail. Selected People survive local
  name filtering and are ordered first when the filter field is blank.
- Multiple People, Albums, and Tags mean intersection. Empty id lists are
  omitted. Parent Tags retain Immich descendant matching.
- Albums and Not in album cannot coexist. Untagged cannot coexist with selected
  Tags. Motion-only cannot coexist with Video. Visibility has exactly one of
  All Accessible, Timeline, or Archive.
- Any, Unknown, Untagged, and Unrated remain distinct at the wire boundary;
  `encodeDefaults=true` cannot manufacture explicit-null filters.
- Start-only, end-only, same-day, leap-day, spring DST, fall DST, and reversed
  date inputs are handled. End is inclusive and submitted boundaries are
  immutable across later pages and device time-zone changes.
- Country/State/City and Make/Model/Lens dependency changes clear invalid child
  drafts, cancel stale reads, and cannot publish prior suggestions. Failed or
  incomplete suggestions do not erase selected values.
- Apply is atomic. Cancel, Back, Escape, outside-click, and sheet swipe do not
  alter applied filters or current results.
- Rapid Apply, query changes, mode changes, chip removal, duplicate near-end
  callbacks, late page responses, and late row-packing completions are rejected
  by submitted-session generation.
- A later-page error keeps existing results and the exact retry page. Pages with
  only unsupported assets are consumed and leave Load more available when a
  valid next page exists.
- Duplicate assets across offset pages are removed by id in first-seen order.
  The app does not claim a transactionally stable server result snapshot.
- Applied ids that disappear from current People/Album/Tag options retain a
  fallback label and remain removable. They are not silently dropped.
- Default visibility preserves current all-accessible, non-Locked server
  behavior and applicable timeline-enabled partners. Generic Search does not
  adopt Favorites' owner-only filtering.
- Search results continue to accept only IMAGE and VIDEO and continue using the
  existing viewer/detail/stack preflight path.
- Narrow bottom sheets and wide dialogs share behavior. Focus, accessibility
  labels, Back/Escape, IME Search, keyboard navigation, and touch dismissal are
  included across Android, iOS, and JVM.

## Type Definitions

- `SearchTextMode`: Context, Filename, Description, OCR.
- `SearchEndpoint`: Smart or Metadata, chosen by a pure pre-I/O selector and
  frozen in a submitted session.
- `SearchCriteria`: normalized immutable text and metadata criteria.
- `SearchSession`: criteria, endpoint, generation, current/next page, and
  consumed pages used by all publication guards.
- `OptionalValue<T>` or a Search-specific equivalent: Any, Unknown, Exact;
  limited to nullable camera/location fields.
- `TagConstraint`: Any, Untagged, Selected stable ids.
- `RatingConstraint`: Any, Unrated, Stars one through five.
- `SearchMediaType`: All, Image, Video plus normalized Motion-only state.
- `SearchVisibility`: All Accessible, Timeline, Archive.
- `TakenDateRange`: optional start and inclusive end calendar dates.
- `SearchCapabilities`: independent Search, Context, OCR, Tags, and Ratings
  availability without collapsing partial failures.
- `SearchTag`: id, parent id, leaf name, full hierarchy value, optional color.
- `SearchSuggestionType` and `SearchSuggestion`: typed camera/location
  dependencies with explicit Unknown.
- Focused immutable option-load and picker presentation states for Idle,
  Loading, Content, and Error/Retry.

## Performance & Cost Impact

- Search keeps page size 50 and justified-row projection; no Mosaic or Room
  result writes are added.
- Server features and preferences add at most one independent read each per
  Explore ViewModel lifetime plus explicit retries.
- People and Albums are observed from existing Room flows. Their existing sync
  is invoked only when the corresponding picker needs data; typing filters
  locally and does not generate network calls.
- Tags load once per destination lifetime when enabled and first opened.
  Camera/location suggestions load lazily and cache successful dependency
  tuples; input changes cancel stale dependent reads.
- Large option-list filtering and selected-first projection run off the main
  dispatcher or use existing efficient immutable projections; Compose items use
  stable ids and bounded thumbnails.
- Request JSON adds only active fields. Result de-duplication uses one id set per
  submitted session and preserves first-seen order.
- There is no additional background worker, startup-global fetch, database
  migration, persistent setting, or platform service cost.

## Backward Compatibility

- Existing Context/Smart and Filename queries remain available through the new
  mode selector and unified request path, with the same page size, results grid,
  density preference, viewer, stacks, and return behavior.
- Servers lacking an optional v2 endpoint or API-key permission retain baseline
  Metadata search; dependent modes/sections show an unavailable/retry state.
- Context and OCR are positively capability-gated. The app never changes query
  meaning through automatic endpoint fallback.
- Existing Room schema version 2, cached People/Albums, logout cleanup, routes,
  settings keys, platform hosts, and API-key validation remain unchanged.
- Search criteria are not persisted, so no saved-state or settings migration is
  needed. Returning to the existing Search destination lifetime follows its
  current ViewModel/navigation-state ownership.
- Full/server-path Search and Find Similar are explicitly out of scope; their
  absence does not remove any currently implemented app behavior.
