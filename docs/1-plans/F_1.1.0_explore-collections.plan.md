# Explore Collections And Stack Browsing Implementation Plan

## Overview

Version 1.1.0 adds three read-only Immich browsing capabilities in serial
phases: viewer-scoped stack browsing, a paginated Favorites collection, and
current "On this day" Memories. The existing Search tab becomes Explore while
retaining smart and filename search; Explore provides static entry cards for
Favorites and Memories, which open dedicated destinations above the Main shell.

Each phase has its own focused tests, cross-platform compile checks, exact
user-flow verification, documentation update, and local commit gate. A later
phase must not begin until the preceding phase passes its gate.

## Problem Statement

ImmichGallery currently decodes stack metadata and displays stack counts, but
it discards the stack identifier at the domain/cache boundary and provides no
way to view the hidden child assets. The app also carries favorite state but
has no Favorites collection, and it has no interface for Immich's generated
"On this day" memories. Adding these independently as new top-level tabs would
crowd the existing four-tab shell, while inserting live collections into
Timeline or Albums would couple them to established cached-screen behavior.

The implementation must preserve the app's read-only boundary, avoid Room and
Mosaic expansion, keep existing Search behavior intact, and explicitly handle
viewer return targets when the currently viewed asset has no visible source
cell.

## Solution Architecture

The work is split into three ordered phases:

1. **Stack browsing:** add stable stack-read API support and a shared, on-demand
   stack session launched from the existing media viewer menu. The stack member
   list remains memory-only and never enters source grids, Room relationships,
   Timeline ordering, or Mosaic inputs.
2. **Explore and Favorites:** rename the Search shell destination to Explore,
   preserve the existing Search ViewModel and search controls, add static
   Favorites and Memories entry cards to the idle Explore state, and implement
   a dedicated live-only Favorites screen using metadata-search pagination and
   justified rows.
3. **Memories:** implement a dedicated live-only current-date Memories screen.
   It renders server memories as year-labelled cover cards and opens one
   memory's ordered supported assets in the existing static media viewer.

New reads follow the existing API -> repository -> UseCase -> ViewModel ->
Compose direction. Favorites and Memories are live-only, matching Search and
expanded asset information; no Room entity, DAO, database version, migration,
or logout cache-clear change is allowed. New API permissions are checked only
when their corresponding feature is opened, so API keys that can browse the
existing library continue to log in normally.

Explore remains one of four Main-shell tabs. `ExploreRoute` replaces
`SearchRoute` inside the nested shell navigation graph. `FavoritesRoute` and
`MemoriesRoute` are root destinations above the Main shell, matching Album and
Person detail ownership and keeping their own top bars, loading, empty, error,
retry, grid/card state, and viewer overlays isolated from Main-shell refresh
and Timeline synchronization.

**Current state**:

`ImmichApiService` supports Timeline, Albums, People, Search, asset information,
and asset edits. `AssetResponse` already decodes nested stack summary metadata,
and `SearchResponse` already represents paged metadata-search results. There is
no complete stack response, memory response, Favorites request, or Memories
request.

**Modifications**:

- Add a serializable stack response containing the stack id, authoritative
  primary asset id, and full `AssetResponse` member list returned by
  `GET /api/stacks/{id}`.
- Add serializable memory and `OnThisDay` response types for the fields consumed
  by the app: memory id, type, memory timestamp, `data.year`, and ordered asset
  list. Unknown response fields remain ignored by the shared JSON client.
- Decode `AssetResponse.ownerId` with an empty default for compatibility. The
  owner id is required to prevent the metadata-search endpoint's implicit
  timeline-partner expansion from leaking partner-owned results into the
  authenticated user's Favorites collection.
- Add `ImmichApiService.getStack(stackId)` using `x-api-key` and the stable
  `/api/stacks/{id}` endpoint.
- Add `ImmichApiService.searchFavorites(page, size)` using a dedicated
  serializable metadata-search request with `isFavorite = true`, descending
  asset order, the requested page/size, and stack-primary behavior consistent
  with normal Immich collections. Do not broaden or make nullable the existing
  filename-search request solely to support Favorites.
- Add `ImmichApiService.getMemories(forDate: LocalDate)` using
  `GET /api/memories` and serialize the `for` query as the exact ISO date-only
  value `YYYY-MM-DD`. Request only current applicable memories; do not call
  create, update, delete, seen, saved, or asset-mutation endpoints.
- Keep endpoint logs free of API keys and credential-bearing media URLs.
- Extend API contract tests to verify stack and memory decoding, missing
  optional memory fields, mixed asset types, Favorites request serialization,
  the current-date query parameter, and malformed pagination token behavior.

**Current state**:

`AssetRepository` exposes live expanded asset information, `SearchRepository`
exposes smart and filename search, and their UseCases map supported image/video
responses into URL-bearing domain assets. Suspend result boundaries use
`runSuspendCatching` so cancellation is not converted into a UI failure.

**Modifications**:

- Add an immutable `AssetStack` domain model with stack id, primary asset id,
  and ordered supported members. Provide pure selection/normalization logic that
  deduplicates member ids, keeps the primary member first when present,
  preserves the remaining server order, and selects the originating asset as
  the initial viewer item when it is still a member, otherwise the primary.
- Add an immutable `Memory` domain model with id, year, memory timestamp, and
  ordered supported assets. Its first supported asset is the cover/origin; a
  memory with no supported image/video assets is omitted from presentation.
- Keep existing `Asset` and `AssetEntity` stack-count storage unchanged. Do not
  add stack id, memory id, or favorite-collection relationships to Room.
- Add `AssetRepository.getAssetStack(assetId)`: fetch current
  `/api/assets/{assetId}` metadata to resolve the current stack id, return a
  successful no-stack result when the asset is no longer stacked, then fetch
  and map `/api/stacks/{stackId}` when present.
- Classify stack permission denial and unavailable/older-server responses into
  explicit failures that the UI can distinguish from a transient connection
  failure. Do not make these failures affect login or the base viewer.
- Expose the existing `/api/users/me` read through `AuthRepository` and a small
  cancellation-preserving `GetCurrentUserUseCase`. `FavoritesViewModel` resolves
  and retains that id only for its destination lifetime; it is never persisted.
- Add `SearchRepository.searchFavorites(page)` and
  `GetFavoriteAssetsUseCase`; reuse the existing supported-type mapping,
  current-server URL construction, and server `nextPage` parsing, but do not
  reuse the underspecified `SearchResult` return type. Define a
  `FavoritesLoadOutcome` containing owned supported assets, the next server
  page, and every successfully consumed server page, plus a typed
  `FavoritesLoadException` containing every page consumed before failure, the
  first unconsumed retry page, and the original cause. The UseCase accepts the
  authenticated owner id, starting page, and the ViewModel's previously
  consumed-page set, then filters every server page by `AssetResponse.ownerId`
  before domain mapping.
- Because Immich metadata search implicitly includes timeline-enabled partners,
  one logical load claim must continue across partner-only or unsupported-only
  server pages until it finds owned supported assets or reaches a terminal
  token. A page is consumed only after its response is successfully decoded;
  merge consumed pages into ViewModel state on both success and typed failure.
  Treat a malformed, repeated, backward, or already-consumed next token as
  terminal after retaining any owned assets from the current successful page.
  If a request fails, retry starts at the exception's first unconsumed page,
  not the logical load's original page. Preserve cancellation without wrapping
  it in `FavoritesLoadException`.
- Add live-only `MemoryRepository.getMemories(forDate: LocalDate)` and
  `GetMemoriesForDateUseCase`. The UseCase filters unsupported/empty memories,
  preserves asset order, groups/sorts display memories by descending
  `OnThisDay` year with stable server order inside a year, and returns a
  cancellation-preserving `Result`.
- Use `Clock.System.now()` and `TimeZone.currentSystemDefault()` only at the
  production ViewModel boundary, deriving a `LocalDate` before crossing the
  UseCase/repository/API boundary. Allow tests to inject both the current
  instant and time zone. A retry recomputes the local date so reopening or
  retrying after local midnight does not reuse yesterday's request.

**Current state**:

source screen's existing order. `DetailTopBarOverlay` offers Slideshow and Info.
Dismissal targets the settled asset because every ordinary pager asset is
expected to have a corresponding source-grid cell.

**Modifications**:

- Add an optional **View stack** item to `DetailTopBarOverlay`. A positive
  `stackCount` shows it immediately, but zero is treated as unknown because
  metadata-search responses omit nested stack details. When the overflow menu
  opens for an unknown settled asset, run one lazy `getAssetStack` preflight,
  keyed by asset id and retained only for the base viewer lifetime. Show a
  non-actionable checking state while it resolves; show **View stack** only for
  a confirmed supported stack, and omit it for a confirmed no-stack result.
  Reuse the existing stack icon and add resource-backed labels.
- Model the unknown-metadata preflight explicitly as
  `Unknown -> Checking -> Available / NoStack / Failed`. `Available` retains the
  resolved stack for action reuse; `NoStack` is published only after a
  successful authoritative no-stack response; and `Failed` retains the typed
  permission, unavailable, or transient error without pretending the asset is
  unstacked. In `Failed`, the menu exposes a resource-backed **Retry stack
  check** action. Reopening the menu does not silently retry or permanently
  suppress access; only the explicit retry transitions back to `Checking`.
- Pass a ViewModel/coordinator-provided suspend `getAssetStack` callback into
  both static and Timeline viewer paths. Existing ViewModels continue to own
  their data dependencies; composables receive callbacks and do not inject
  repositories or UseCases.
- Add `StackSessionOverlay` as an ephemeral nested viewer session. It owns only
  request/loading/error/retry/session UI state and receives its read callbacks
  from the parent viewer. On success it reuses `StaticPhotoOverlay` for the
  normalized supported stack member list with stack recursion disabled.
- Reuse the preflight result when **View stack** is selected so a sparse Search,
  Album, Person, Favorites, or Memories list response does not require a second
  stack read. For assets whose list response already supplies a positive stack
  count, defer the authoritative two-read resolution until selection. At most
  one stack resolution may be active per settled asset, and changing assets or
  closing the viewer cancels or invalidates it.
- Freeze the initiating asset id when the request starts. Cancel or ignore the
  result if the user closes the viewer, starts a newer stack request, or pages
  the base viewer to another asset before the response publishes.
- While the nested stack session is visible, suspend base-pager input,
  slideshow, gestures, shortcuts, and video playback so two viewer layers
  cannot respond or play simultaneously.
- Back, Escape, and drag-dismiss close the stack session first and restore the
  unchanged base viewer at the initiating asset. A second dismissal returns
  through the base viewer's existing grid-target behavior. Stack children are
  never reported to the source `PhotoOverlayHost` as grid return targets.
- Keep stack member Info, image zoom, authenticated video playback, paging, and
  slideshow behavior on the existing viewer components.
- Show actionable local messages for no-longer-stacked, permission-denied,
  unavailable-server, transient request failure, and no-supported-members
  outcomes. None may close or replace the base viewer.
- Add pure state/selection tests covering normalization, initial item,
  duplicate ids, unsupported members, stale request rejection, layered back
  behavior, origin preservation, and every availability preflight transition.
  Cover permission and transient `Failed` states, explicit retry, and proof
  that failure never becomes `NoStack`. Include the regression where a static
  source response has no nested stack/count but the `/assets/{id}` detail
  response is stacked. Extend Timeline overlay tests to prove a stack session
  cannot change its bucket/asset grid return target.

  session from Timeline restores the same Timeline asset/bucket target.
- State explicitly that Explore cards do not prefetch and Memories does not
  alter Timeline cold/cached/manual sync behavior.
- Do not update workflow/testing guidance because the durable workflow and test
  policy are unchanged.

## Technical Considerations

- **Layering**: All new reads follow API service -> repository -> UseCase ->
  ViewModel callback -> Compose. Existing and new ViewModels never inject
  repositories directly. Koin owns repository, UseCase, and ViewModel wiring.
- **Read-only scope**: Feature flows use the existing `GET /users/me` identity
  read plus new `GET /assets/{id}`, `GET /stacks/{id}`, filtered
  `POST /search/metadata`, and date-only `GET /memories` reads. There are no
  server mutations, favorite toggles, memory seen/save/hide calls, or stack
  edits.
- **Cache ownership**: Stack lists, Favorites, and Memories are live-only and
  memory-resident. Room remains schema version 2. Favorites row density is a
  lightweight setting cleared through the existing preference/session policy.
- **Async correctness**: Every request has cancellation and stale-generation
  guards. Pagination preserves server tokens, prevents duplicate claims and
  repeated-token loops, reports consumed and first-unconsumed pages, filters
  partner-owned Favorites across sparse pages, and keeps existing assets after
  later-page failure. Stack requests are tied to the initiating viewer asset
  and session lifetime; a failed availability check remains retryable and is
  never cached as a successful no-stack result.
- **UI and layout**: Search remains RowPacking-only inside Explore. Favorites
  also uses RowPacking; Memories uses cover cards. No new screen uses Mosaic.
  Existing shared viewers, media authentication, strings, icons, dimensions,
  scrollbars, and return-source helpers are reused.
- **Platform impact**: Implementation stays in shared code. Android, iOS, and
  JVM keep their current Coil and video-player paths. No platform permission or
  host change is required.
- **Security**: API keys remain in configured headers, except the existing JVM
  video query behavior. No new log may include a key or authenticated media
  URL. Fine-grained permission errors are shown only after the user invokes the
  corresponding feature.
- **Verification and docs**: Every phase runs focused tests and shared compile
  gates, performs grep checks for prohibited/nonlocalized code, updates its
  canonical docs, stops Gradle daemons, and creates a local commit before the
  next phase.

## Edge Cases Considered

- A stack badge may be stale, the asset may no longer belong to a stack, or the
  stack may be deleted between the asset-info and stack calls.
- A stack may return one member, duplicate ids, omit the declared primary,
  contain unsupported asset types, or return fewer supported members than its
  displayed server count.
- A stacked asset opened from Album, Person, Explore Search, Favorites, or
  Memories may not be the stack primary. The originating member is selected
  when present; otherwise the normalized primary is selected.
- A stack request can race with paging, a second request, base-viewer dismissal,
  configuration change, or screen disposal. Only the latest still-relevant
  request may publish.
- An unknown-stack preflight may fail before **View stack** exists. Permission,
  unavailable, and transient failures remain distinct `Failed` states with an
  explicit retry action; reopening the menu neither auto-retries nor converts
  the failure to `NoStack`.
- A nested stack session must consume Back/Escape/drag before the base viewer,
  prevent double video playback, and return to its initiating base asset rather
  than a hidden stack child.
- API keys may omit `stack.read` or `memory.read`; older servers may return 404
  for an endpoint. Existing browsing and login remain usable and the invoked
  feature reports an actionable local state.
- Favorites may be empty, contain one item, return an unsupported-only page,
  include timeline-enabled partner assets, return several partner-only pages,
  return a malformed/repeated/terminal next token, or fail after earlier pages.
  Only assets owned by the authenticated user are displayed; valid owned
  results behind sparse pages remain reachable. Existing pages remain visible
  and failed tokens remain manually retryable.
- A Favorites logical load may consume sparse page `1` before page `2` fails,
  or a later page may point backward to an already consumed page. Typed success
  and failure contracts preserve consumed progress, retry only the first
  unconsumed page, and terminate malformed/repeated/backward chains without
  revisiting an earlier page.
- Rapid Favorites load-more triggers, width changes, zoom changes, route exit,
  and viewer return cannot publish duplicate pages or stale row projections.
- Explore cards appear only for a blank idle search. Typed or executed search
  state is not overlaid by collection cards, and clearing restores the landing
  state without changing saved Search density.
- Current Memories may be absent, include multiple memories for the same year,
  contain no supported assets, or cross midnight while the screen is open. A
  retry/reopen recomputes the current calendar date in the system time zone;
  UTC must not determine the day near local midnight. No background midnight
  timer is introduced.
- Memory asset ordering remains server-defined. Card grouping changes only
  memory-card order, not asset order inside a memory.
- Paging within a memory has no grid cell for non-cover assets. Dismissal always
  targets the selected cover while Info, playback, slideshow, and stack actions
  continue to use the settled asset.
- Empty, single-item, first, last, and mixed image/video viewer states retain
  existing clamping, playback, zoom, slideshow eligibility, and drag behavior.
- Android, iOS, and JVM share state and navigation behavior; platform-specific
  authenticated image/video implementations are not bypassed or duplicated.

## Type Definitions

- `AssetStack`: immutable stack id, primary asset id, and normalized supported
  assets, with pure initial-selection behavior.
- `Memory`: immutable memory id, OnThisDay year, memory timestamp, and ordered
  supported assets; cover is the first supported asset.
- `FavoritesState`: assets, justified rows, initial/load-more state, error,
  server token/page guards, consumed server pages, first-unconsumed retry page,
  authenticated owner id, request generation, width/viewport, and row density.
- `FavoritesLoadOutcome`: owned supported assets, next server page, and all
  successfully consumed pages for the logical claim.
- `FavoritesLoadException`: typed non-cancellation failure with successfully
  consumed pages, the first unconsumed retry page, and original cause.
- `MemoriesState`: memory groups/list, initial/error state, request generation,
  and selected memory id.
- `PhotoOverlayReturnTarget`: current-asset default versus origin-asset policy.
- `StackAvailability`: viewer-local `Unknown`, `Checking`, `Available`,
  `NoStack`, or retryable `Failed` state for assets whose list response omits
  stack metadata.
- Typed stack access failures and `StackUiMessage`, `FavoritesUiMessage`, and
  `MemoriesUiMessage` values for actionable presentation without raw server
  exceptions in Compose.

No new persisted entity, DAO, database relation, migration, Mosaic scope, or
platform-specific interface is introduced.

## Performance & Cost Impact

- Stack browsing performs at most one two-read resolution per settled asset in
  a base-viewer session: current asset information, then the complete stack.
  For an asset with unknown stack metadata this starts only when the overflow
  menu opens; for a known stacked asset it starts when **View stack** is
  selected. The result is reused by the action and retained only for that base
  viewer lifetime. A failed unknown-metadata preflight performs another
  resolution only after the user selects **Retry stack check**.
- Favorites performs one existing `/users/me` read when the destination opens,
  then requests server pages of 50 items. One logical UI load can traverse
  multiple partner-only or unsupported-only server pages before returning owned
  assets or terminal state. Requests and row packing remain cancellable; no
  Favorites request occurs before its destination opens.
- Explore cards are static; merely selecting the Explore tab creates no new
  Favorites or Memories traffic.
- Memories performs one local-date list request when its destination opens or
  retries. Server-returned assets reuse existing Coil/video caching and no
  additional original media is prefetched beyond current viewer behavior.
- No Room write, migration, cache invalidation, Timeline sync, foreground
  service, or Mosaic CPU/IO cost is added.
- New row/card projections run outside composition; stale work is cancellable
  and guarded before publication.

## Backward Compatibility

- Room remains schema version 2 with no migration or exported-schema change.
- Existing credentials, Search row density, Timeline grouping, Mosaic settings,
  cached library content, and platform media behavior remain valid.
- `SearchRoute` is an in-memory nested destination, so replacing it with
  `ExploreRoute` does not migrate durable user data. Search functionality and
  its settings scope remain intact.
- Favorites adds a new optional settings key with the existing default density
  fallback; absence is valid for all existing installs.
- API keys without new fine-grained scopes can still connect and use existing
  features. Stack or Memories access reports a local permission state only when
  invoked.
- Servers without the stable stack or Memories endpoints leave the base viewer
  and other screens usable and report that the selected feature is unavailable.
